### 1. 地形防御補正の実効値（→ #41）

戦車（攻撃75・HP100）→ 歩兵（HP100）で、防御側の地形だけを変えたときの `forecastCombat` の結果:

| 防御側の地形 | `defense` | 与ダメージ |
| --- | --- | --- |
| 道路 | 0 | 75 |
| 平原 | 1 | 74 |
| 森林 | 2 | 74 |
| 都市 | 3 | 73 |
| 山岳 | 4 | 72 |

最強地形と最弱地形の差は 3 ダメージ（4%）。`src/game/combat.ts:56` の `reduction = defenseStars * hp / 100` は、HP100 のとき上限が 4 にしかならず、`1 - reduction / 100` が最大 4% の軽減で頭打ちになる。

### 2. 間接ユニットの移動後射撃（→ #47）

```
moveUnit(s, 'r1' /* artillery */, { x: 2, y: 0 })  // => ok
attackUnit(moved, 'r1', 'b1')                      // => ok
```

`attackUnit`（`src/game/commands.ts:137-145`）は `hasActed` のみを検査し `hasMoved` を見ないため、間接ユニットが移動と射撃を同一ターンに行える。

### 3. 移動範囲と実移動の不整合（→ #46）

10×1 の平原、赤の歩兵 (0,0)（視界2・移動3）、青の戦車 (3,0)（未索敵）:

```
reachablePositionsForPlayer(s, 'r1', 'red')  // => (1,0) (2,0) (3,0)
moveUnit(s, 'r1', { x: 3, y: 0 })            // => { ok: false, error: 'Destination is occupied' }
```

#32 の修正で移動範囲の表示からは霧の情報が消えたが、**ハイライトされたマスが実際には移動できない**という形で漏洩経路が残っている。

## 全体所見

### 良い点

- **ゲームロジックと UI の分離が徹底されている。** `src/game/` は DOM に一切依存せず、「状態 + コマンド → 新状態」で統一されている。セーブ・リプレイ・キャンペーン・エディタがこの基盤の上に自然に載っており、Issue #1 で掲げた設計方針が実際に守られている
- **入力の検証が厳格。** `unknown` からの検証、サイズ上限、スキーマバージョン、シナリオ定義との照合まで一貫している。壊れたデータで画面が落ちない
- **前回レビューの12件がすべて修正済み。** テストも 113 件から 134 件に増えており、指摘が確実に潰されている

### 弱点の傾向

今回の指摘は、大きく3つの傾向に分類できる。

1. **数値設計が実装に追いついていない**（#41, #47, #48）— システムは配置されているが、実効値が意図した効果を生んでいない。地形・間接砲・燃料はいずれも「ルールとしては存在するが戦術に影響しない」状態で、戦略ゲームとしての厚みを削いでいる。優先度としては #41 が最も大きい
2. **UI 層が検査の外にある**（#42, #44, #46, #51, #52）— `src/game/` の品質に比べ、`src/main.ts` は無検査・単一関数・全置換描画で、今回の不具合が集中した。#52 の基盤整備が他の再発防止にも効く
3. **拡張の単位が定義されていない**（#43, #49, #50, #53-5）— ユニット追加・スキーマ変更・シナリオ設計といった「今後必ず発生する変更」に対して、手順と単一のソースが無い。機能を足すほど手戻りが増える構造

### 推奨する着手順

1. #41（地形防御）— ゲーム体験への影響が最も大きく、変更範囲は小さい
2. #42（未エスケープ出力）— 修正は1行、放置するとシナリオ共有機能の前提が崩れる
3. #52（テスト基盤）— 以降の修正すべての安全網になる
4. #45 → #44（AI 性能 → 逐次描画）— 順に対応すると CPU ターンの体験がまとめて改善する
5. #50（データ駆動化）— #53-5（対空ユニット）など今後の機能追加の前提
