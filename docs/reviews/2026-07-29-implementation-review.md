## 実測による裏取り

### 1. CPU が毎ターン不正コマンドを出している（→ #61）

全 5 シナリオ × 3 難易度を CPU 対 CPU で 120 ハーフターンまで回し、`applyGameCommand` の失敗回数を数えた（失敗時は `runCpu` と同じくターン終了に置換）。

| シナリオ/難易度 | 決着 | 不正コマンド |
| --- | --- | ---: |
| skirmish/easy・normal・hard | なし | 64 / 72 / 75 |
| islands/easy・normal・hard | なし | 16 / 49 / 25 |
| landing/easy・normal・hard | blue (19T) | 1 / 3 / 3 |
| canyon/easy・normal・hard | なし | 76 / 67 / 72 |
| siege/easy・normal・hard | red (51T) / なし / なし | 63 / 74 / 73 |

失敗はすべて `move → Unit has already acted`。原因は `src/ai/rules.ts:304` の `if (unit.hasMoved) continue;` が `hasActed` を見ていないこと。`src/main.ts:724` が失敗を一律 `endTurn` に変換するため、**CPU は最初の攻撃直後にターンを終える**。

同行を `if (unit.hasMoved || unit.hasActed) continue;` に変えて再計測:

| | 変更前 | 変更後 |
| --- | ---: | ---: |
| 不正コマンド | 16〜76 件 | 全組合せ 0 件 |
| 決着した組合せ | 2 / 15 | 10 / 15 |
| landing | blue が 19T でタイムアップ勝ち | red が 10〜14T で上陸・占領して勝利 |

### 2. 燃料切れ判定のタイミングがずれている（→ #62）

`src/game/commands.ts:231-237` の枯渇判定が `refreshed` 全体を対象にしているが、補給・毎ターン消費（同 218-230）は新しい `activePlayer` 側にしか適用されない。

```
戦闘機（燃料3）を自軍都市 (3,0) へ移動（コスト3、燃料0）
endTurn(red)  → 戦闘機が消滅（補給を受ける手番を迎える前に喪失）

戦闘機（燃料2）を平原 (2,0) へ移動（燃料0）
endTurn(red)  → 戦闘機が消滅（次の自分の手番開始ではなく、自分のターン終了時）
```

README の「手番開始時に燃料・弾薬が全回復」「拠点の外で手番を迎えるたびに燃料を消費し、0 になると失われます」および UI の「補給まで残り N 行動機会」表示と、実際の喪失タイミングが 1 手番ずれている。

### 3. 危険域表示が機能していない（→ #63）

`endTurn`（`src/game/commands.ts:218-230`）は `hasMoved` / `hasActed` を手番を受け取る側にしかリセットしない。`enemyThreatPreview`（`src/main.ts:84-108`）はそのフラグで敵の行動可能性を判定しているため、前ターンに行動した敵の危険域が抜ける。

`skirmish` を CPU（普通）に数ターン動かし、赤のターン開始時点で比較:

| 敵ユニット | UI が表示する危険域 | 実際の危険域 |
| --- | ---: | ---: |
| b1 (infantry, `hasActed`) | 0 タイル | 32 タイル |
| b2 (tank) | 43 | 43 |
| b3 (recon) | 62 | 62 |
| u1 (infantry) | 22 | 22 |
| u2 (artillery, `hasActed`) | 0 タイル | 72 タイル |

視認できている 5 部隊のうち 2 部隊が危険域 0 として描画された。攻撃してきた敵ほど非表示になる。

### 4. 占領進行度が陣営別でない（→ #64）

```
中立都市 (capturePoints 20) を赤歩兵が1回占領   → 10
赤歩兵をそのマスで撃破                          → 10（戻らない）
青歩兵が (1,0) へ移動                           → 10（戻らない）
青歩兵が1回占領                                 → owner: 'blue'
```

`releaseCaptureProgress`（`src/game/commands.ts:87-93`）は移動する側の出発マスにしか効かず、撃破と敵の進入では戻らない。本来 2 ターン必要な占領が 1 ターンで完了する。

### 5. 間接ユニットが反撃する（→ #66）

```
rocket (射程3-5) が距離3 の artillery (射程2-3) を攻撃
→ rocket    hp 100 → 88   （反撃を受けた）
→ artillery hp 100 → 19
```

`forecastCombat`（`src/game/combat.ts:60-65`）の反撃判定は距離しか見ないため、Issue #1 §2.4「間接攻撃は反撃なし」は距離の偶然でしか成立していない。移動済み（`hasMoved: true`、上記 3 と同じ理由で非アクティブ側は保持される）の間接ユニットも反撃できるため、#47 で入れた制約も反撃では回避される。

### 6. その他コードで直接確認した事実

- `src/ai/rules.ts:307, 267, 292` — CPU の移動候補列挙が `reachablePositions(state, ...)`（完全情報）。未索敵の敵が障害物になり、README の「視認済み情報だけを用いて行動」に反する（→ #65）
- `src/ai/rules.ts:66-75` — `reachablePositions` は現在地を除外するため、CPU は「留まる」を選べない（→ #65）
- `src/main.ts:401` — `maps.find(candidate => candidate.id === stage.scenarioId)!` が `campaignCards` 生成で無条件に評価される。組み込みシナリオが緊急フォールバックに落ちた場合に例外で白画面になる。`scenarioLoadError` も UI から参照されていない（→ #67）
- `src/game/commands.ts:203` — `disembarkUnit` が `transport.hasMoved` を拒否するため、航行したターンに上陸できない。README・Issue #20 §6.2 のいずれにも記載がなく、上陸作戦は最短 4 ターンかかる（→ #68）
- `README.md` — アーキテクチャ図の `units.ts` が「9種」のまま（実装は 10 種）（→ #68）
- `src/ai/rules.ts:140, 158` — `productionAction` / `objectives` に未使用引数。lint が無いため検出されない（→ #52）
- `.github/workflows/pages.yml` — `npm run build` のみでデプロイする。`ci.yml` のテストが落ちていても Pages は公開される（→ #52）

## 全体所見

### 目的は達成できているか

**コア部分は達成している。** Issue #1 が掲げた「生産 → 移動 → 攻撃 → 占領のサイクル」「UI とロジックの完全分離」「コマンド経由の状態遷移によるリプレイ・undo」は実装され、Phase 5（セーブ・リプレイ・シナリオ・キャンペーン・エディタ）と Phase 6（港湾・輸送艦・上陸）まで積み上がっている。前回レビューで最大の問題だった地形防御の実効値（#41）も修正され、地形選択が戦術的に意味を持つようになった。

**一方で、直近に追加した3つの機能が期待どおりに動いていない。**

| 機能 | 追加元 | 現状 |
| --- | --- | --- |
| CPU の難易度別評価重み | #53-4 | CPU が 1 手でターンを終えるため発現しない（#61） |
| 敵の危険域表示 | #53-2 | 前ターンに行動した敵が危険域 0 として描画される（#63） |
| 燃料 attrition | #48 / #59 | 喪失タイミングが 1 手番早く、補給拠点上でも失われる（#62） |

いずれも `src/game/` の純粋関数としては正しく、**「状態のライフサイクル」と「UI／AI の前提」の接合部**で壊れている。#61 は `hasActed` の見落とし、#62 は補給対象と枯渇対象の範囲不一致、#63 は非アクティブ側のフラグが残る前提の取り違え。3 件とも既存 151 件のテストを 1 件も落とさずに成立している。

### 弱点の傾向

1. **ターン境界の状態管理に単一の定義がない**（#62, #63, #64, #66）— 「手番の切り替わりで何がリセットされ、何が残るか」がコード上のどこにも明文化されておらず、`endTurn` の 1 関数に暗黙のルールが同居している。フラグ・燃料・占領進行度が三者三様に扱われ、参照側（UI・AI）が別の前提を持ってしまった
2. **統合レベルの検証が無い**（#61, #63, #67）— `src/game/` の単体テストは充実しているが、「CPU が最後まで行動できるか」「UI が正しい情報を出すか」「起動できるか」を確かめる層が存在しない。#52 が未着手のまま機能追加を続けたことのコストが、今回の3件で顕在化した
3. **霧の扱いがプレイヤー側と CPU 側で非対称**（#46, #65）— どちらも「未索敵の敵をどう扱うか」の一貫した規則が無いことに起因する。片方だけ直すと非対称が残るため、同時に方針を決める必要がある

### 推奨する着手順

1. **#61**（1 行の修正 + 回帰テスト）— CPU がまともに行動しない現状が、他のすべての体験を覆っている。効果対コストが圧倒的
2. **#62**（枯渇判定の対象を絞る）— 部隊が理不尽に失われるため、プレイ体験への影響が直接的
3. **#52 の項目 2**（CPU 対 CPU 完走テスト）— #61 の回帰防止がそのまま #30 の受け入れ条件を満たす。以降の AI 変更すべての安全網になる
4. **#63**（ターン境界のフラグ規則を決める）— #66 の反撃ルールと同じ根に触るので、方針を先に確定させる
5. **#46 → #65**（霧の規則を左右対称にする）
6. **#64**（占領進行度の陣営別管理）— セーブスキーマに触るため #43 と併せて設計する
7. **#52 の項目 1・3・5**（jsdom テスト / lint / デプロイのゲート）— 今回の #63・#67 の再発防止
