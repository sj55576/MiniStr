## コントリビューションと CI

外部 fork の pull request も typecheck、test、build を実行します。CI は read-only の `contents` 権限だけを持ち、リポジトリの秘密情報は利用しません。Pages は `main` への push でのみ、同じ検証の成功後にデプロイされます。あわせて、追加されたコミットメッセージに私的セッション URL が含まれないことを CI が検査します。詳細は [CONTRIBUTING.md](../CONTRIBUTING.md) を参照してください。

### 履歴の書き換えでは除去できません

9 件のうち 7 件は pull request の head コミットそのものです。GitHub は close 済み pull request の `refs/pull/<番号>/head` を恒久的に保持するため、`main` を書き換えて強制更新しても、これらのコミットは SHA を指す URL と pull request の Commits タブから引き続き参照できます。つまり「履歴書き換えによる完全除去」は成立しません。315 コミット分の SHA が変わり、既存 issue・pull request 中の SHA 参照が壊れる代償だけが残ります。

完全な除去を要件とする場合、実際に効果があるのは次のいずれかです。

- squash した履歴で新しい公開リポジトリを作成し、現リポジトリは非公開のまま保管する。fork・star が 0 の現時点なら影響は小さいものの、issue と pull request の議論は失われます。
- 履歴を書き換えたうえで、到達不能オブジェクトと残存する pull request ref の削除を GitHub サポートに依頼する。

### 公開判断

セッション URL は当該アカウントに紐づき、第三者が開いても内容を参照できないため、認証情報とは扱いが異なります。上記の代償に見合わないため、**この 9 件の残存を公開の妨げとはしません**。

再発防止は文書だけでは不十分です。セッション URL の行はツールが自動で付与するため、レビュー時の目視や PR テンプレートのチェック項目では見落とされます。実際、最後の混入は #93（2026-08-01）で、公開前確認の作業中にも発生していました。`scripts/check-private-links.sh` が pull request の追加コミットのメッセージを走査し、該当があれば CI を失敗させます。寄稿者は `npm run check:links` で同じ検査をローカル実行できます。
